# Canonical domain model

Identifiers are UUIDs generated by the owning context. External identifiers are never canonical IDs.

The lists below define the intended canonical vocabulary. The first slice currently
persists organizations, memberships, projects, intake requests, specification
versions, approvals, work items, connector installations/repositories/webhook
deliveries, provider configurations, runner pools/runners, executions/events, and
simulated pull-request references. Clients, clarification records, decomposed
requirements/decisions, milestones, attempts, artifacts, previews, and append-only
cost entries remain to be implemented.

## Control plane

- `Organization` is the tenant root.
- `User` is an OIDC subject; `Membership` assigns an organization role and optional project/client grants.
- `Client` represents the requirement owner and may have restricted members.
- `Project` owns intake policy, repository choices and delivery policy references.
- `IntakeRequest` preserves the original structured request and clarification history.
- `Specification` is a stable identity with immutable `SpecificationVersion` snapshots.
- `Requirement` and `Decision` capture approved scope and rationale.
- `WorkItem` is generated from one approved specification version and must be reviewed before execution.
- `Approval` records actor, subject, version, decision, reason and timestamp.

## Integrations

- `ConnectorInstallation` identifies a provider account/installation and lifecycle state.
- `RepositoryConnection` is an authorized repository exposed by an installation.
- `ExternalReference` contains provider, account/installation, repository/project, resource type and external ID.
- `WebhookDelivery` provides signature result, deduplication and processing status.
- `ModelCredential` stores tenant-owned metadata and a `SecretReference`; the secret
  value exists only in the configured secret-store adapter.

## Delivery

- `AgentProviderConfiguration` selects provider, runtime, model and authentication mode while storing only secret references.
- `ProviderVerification` is an asynchronous, runner-leased probe of the exact
  provider/runtime/model/authentication selection and records only sanitized status
  and usage.
- `Runner` and `RunnerPool` represent execution capacity and policy.
- `Budget` sets cost, duration, turn and attempt limits.
- `Execution` is a durable delivery request; `Attempt` is one bounded agent/verification cycle.
- `ApprovalRequest` pauses an execution at a policy checkpoint.
- `ExecutionEvent` is a user-safe normalized timeline record, never hidden chain-of-thought.
- `Artifact` stores metadata, content hash and object-store locator.
- `VerificationResult` records independently observed commands and outcomes.
- `CostEntry` records measured usage and the price-catalog version or an explicit unknown price.
- `DeliveryResult` associates commits, pull requests, checks and previews through external references.

## Lifecycle

```text
INTAKE_RECEIVED -> CLARIFICATION_REQUIRED -> SPECIFICATION_DRAFTED
-> AWAITING_APPROVAL -> SPECIFICATION_APPROVED -> WORK_ITEMS_GENERATED
-> WORK_ITEMS_REVIEWED -> READY_FOR_EXECUTION -> BUILDING
-> VERIFICATION -> DELIVERED | FAILED | AWAITING_HUMAN
```

Transitions are commands guarded by aggregate state and permission checks; callers cannot set status fields directly.
